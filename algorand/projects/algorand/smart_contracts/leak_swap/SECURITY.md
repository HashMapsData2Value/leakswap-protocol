# Sponsored Call Constraints

The application requires `setReady`, `leakyClaim`, `leakyRefund`, and
`punishRefund` to use exactly two outer transactions: the sponsor payment at
index 0 and the application call at index 1. Both transactions must have zero
rekey destinations. The payment must have zero fee and the exact method-specific
receiver, amount, and close-out destination. Existing caller, deadline, readiness,
completion-mode, and signature checks still apply.

The application derives the required payment sender from the exact FeeSponsorLSig
bytecode parameterized by its application ID and stored Ali/Xin addresses.
It does not accept a caller-registered sponsor or a self-funded substitute payment.
The LogicSig independently enforces the group shape and its spending conditions.
Creation and read-only calls do not require sponsor payments.

`npm run build` runs `scripts/generate-sponsor-address.mjs` before compilation.
The generator extracts fixed bytecode segments from the installed compiler's
sponsor output, verifies reconstruction against four independently compiled
fixtures (including the maximum uint64 application ID), and regenerates
`sponsor_address.algo.ts` and the address fixtures. The address is
SHA-512/256 of the `Program` domain prefix followed by program bytes.
Never edit the generated bytecode segments manually. Compiler or sponsor changes
must regenerate the helper, and the resulting address must also match the
Algod-assembled sponsor used by clients before release.

These changes require new application deployments and new sponsor programs.
Existing deployed applications and funded sponsor addresses are not upgraded.
Clients and wallet artifact verification must adopt matching application and
sponsor artifacts together; keep the original program for existing sponsors.

Offline tests cover group layout, substitute sponsor senders, payment fields,
rekeying, address derivation, and existing signature/timing/fee boundaries.

## Round Deadlines

`t0` and `t1` are absolute Algorand round numbers, not Unix timestamps.
Creation requires `t1 > t0 > Global.round`. Early refund is allowed through
round `t0` (`<= t0`) only before Ready. Claim requires Ready or `round > t0`,
and always requires `round < t1`. Punishment starts at `round >= t1`.

The offline boundary matrix covers `t0 - 1`, `t0`, `t0 + 1`, `t1 - 1`, `t1`,
and `t1 + 1`, both before and after Ready. Chain-halt regressions jump the
timestamp to 4,000,000,000 while holding round 999 or advancing it to 1000:
the contract remains Ready, a correctly sponsored punish attempt is rejected,
and Xin can claim using a valid leaky signature and the designated sponsor.
Timestamp jumps cannot consume the round-based claim window.

LocalNet tests construct deadlines from a read-only Algod status round, using
20 rounds per minute for the one-hour and later deadline offsets. Wall-clock
time is not used to construct contract deadlines.

`contract.e2e.spec.ts` runs against LocalNet using disposable accounts and the
generated application and sponsor artifacts. It covers:

- Algod assembly parity for all four generated sponsor-address fixtures.
- Successful ready/claim with a zero-funded Xin, platform-fee accounting,
	signature recovery, and application deletion.
- Successful early refund, application deletion, and empty sponsor/escrow accounts.
- 24 application rejection attempts across all four sponsored methods: substitute
	sender, prefix, suffix, repeated pair, reversed pair, and application rekey.
- Six real LogicSig rejection attempts: prefix, suffix, repeated pair, reversed
	pair, payment rekey, and nonzero payment fee.
- Unchanged participating balances and readiness after rejected attempts; no
	sponsor rekey after the LogicSig attacks.

These tests exposed an early-refund opcode-budget regression. Claim and refund
now reserve 2400 remaining opcode units after sponsor validation and before
signature verification. The LocalNet tests exercise the existing 7000-microALGO
pooled settlement fee without increasing it.

From the Algorand project directory, regenerate artifacts and run offline checks:

```sh
npm run build
npm run check-types
npx --no-install vitest run smart_contracts/leak_swap/contract.spec.ts smart_contracts/leak_swap/sponsor_lsig.spec.ts
```

The build only regenerates artifacts and clients; it does not deploy contracts.
Run `contract.e2e.spec.ts` separately only when node-backed transactions are
intended. LocalNet must already be running; those tests do not reset it. The current
node-backed suite does not certify successful expired `punishRefund`, public-chain
execution, or wallet/swap-page integration with these new artifacts. Deadline
boundary and punishment behavior remain covered by the offline suite. Matching
client artifact adoption and further release validation are still required before
publishing or using the new artifacts with funds.
